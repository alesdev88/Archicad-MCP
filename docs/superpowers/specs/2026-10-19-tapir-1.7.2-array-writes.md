# Tapir 1.7.2 array writes: Swept Beam and Road Marking (19.10.2026)

**Question.** Do `create_swept_beam` and `create_road_marking` keep working once Tapir 1.7.2 is
released? **Answer: no, not as they were; both are now version aware.** Tapir up to 1.7.1 takes
the old write unchanged; 1.7.2 and newer gets a new write sequence, verified live.

## What changes in Tapir 1.7.2

Upstream main (reports 1.7.2, unreleased on 19.10.2026) carries #558 (commit 8271dbba), the fix
for #557. In `SetGDLParametersOfElements` (archicad-addon/Sources/ElementGDLParameterCommands.cpp):

- A list value is written item by item through `ACAPI_LibraryPart_ChangeAParameter` with
  `ind1`/`ind2`. A list whose size differs from the parameter's `dim1 x dim2` is refused:
  "resizing an array parameter is not supported". Up to 1.7.1 the list replaced the array in the
  parameter block by hand, at any size, without the Parameter Script.
- Every `ChangeAParameter` runs the part's Parameter Script with `GLOB_MODPAR_NAME` set to the
  parameter, and Tapir re-reads the block after each item, so the dimension check of the next
  list sees what the script made.
- Unchanged: single values and `index1` items are written in list order; all list values are
  applied after them, in list order. One element is one undo step, and an error on any item
  commits nothing for that element.

## What the parts do

Neither part has a size parameter. Both Parameter Scripts take `n = VARDIM1 (nodeX)`, pad the
other node arrays to `n` and write every array back with exactly `n` items. Only the parts' own
reactions change `n`: a fresh path (a changed `A` that was not typed, `GLOB_MODPAR_NAME <> "A"`)
makes it 2; an insert or add-node grip drag adds one; the merge (a node within 1 cm of its
neighbour in plan, when `GLOB_MODPAR_NAME` is `nodeX`, `nodeY` or `nodeZ` and `n > 2`) removes
one. The Road Marking skips the merge on a run that repairs array lengths; the Swept Beam does not.

The old tools write every node array as a list, of a new size on every placement (the part starts
with 2 nodes) and on most updates, and `segArc` in radians.

## Live findings

MCP-Test_27, Archicad 27 (6080), Tapir built from `~/Developer/tapir-fix-morph-rotation` (upstream
main a4e4a745 with #558, plus the ModifyMorphs rotation fix bd23f1b5), reporting 1.7.2. Archicad
27 rather than 29 because swapping the AC29 bundle means quitting every AC29 instance, and one
held a production project. Both parts are Archicad 27 builds, and `ChangeAParameter` is the same
API in 27 to 30. The AC27 bundle was restored to the official 1.7.1 afterwards (sha1 31dfdd80).

1. A list of another size is refused, as the source says ("has 2 x 1 items, but 3 x 1 were
   given").
2. **Angle items take degrees.** `segArc` written as `[0, 0, 45, 0, 0]` reads back 0.785398
   (radians); an `index1` item of 30 reads back 0.523599. Single angles already took degrees.
   Reads stay in radians.
3. **The merge fires on item writes.** Writing `nodeY` then `nodeX` whole, where an intermediate
   state put two nodes on top of each other, dropped a node mid-write; the next item failed
   ("Failed to change item 5,1 of array parameter nodeY") and nothing was committed.
4. **The parts' own grips resize the arrays.** On a Swept Beam: `A = 1`, `aDone = 2` reset the path
   to two nodes at x 0 and 1 (and squared the end cuts: a 20 degree start cut read 0 after it);
   three `extEnd` writes, each 1 m past the last, added a node each: x 0, 1, 2.25, 3.5, 4.75.

## The new write (Tapir 1.7.2 and newer)

`placed_path.writes_items` reads `GetAddOnVersion` (an unknown version keeps the old write). Then
one `SetGDLParametersOfElements` call per element, in this order:

1. `pp.resize_writes`: `A = 1`, `aDone = 2` (the fresh path reset, the same in both parts; the
   Road Marking keeps `A` at 1 anyway), then `count - 2` writes of `extEnd`, each 1 m past the
   last, read from the element first (`GetGDLParametersOfElements`, after `CreateObjects` for a
   new one). The path is then `count` nodes on a straight line along x, 1 m and more apart, every
   helper array zero, the add-node grips balanced.
2. The tool's single values as before. The Swept Beam writes its own end cuts again when the call
   does not set them (read in radians, written in degrees), since the reset squares them.
   The extension grip pairs are not written: a lone `extEnd` write would be a drag.
3. The lists: `nodeY` parked (1 m apart, 10 m clear of every real y), `nodeX`, the real `nodeY`
   (`pp.parked_xy`), then `nodeZ`, the rest, `segArc` in degrees. At every item consecutive nodes
   stay at least 1 m apart, or both are final; `test_placed_path.py` simulates the merge over the
   whole write for random paths.

A path with two consecutive nodes closer than 1 cm in plan (a vertical piece) is refused before
anything is placed (`pp.check_plan_gaps`): the merge would fail the write. Up to 1.7.1 such a
path is written and merges on the next drag, as before.

The dry run reports `array_writes`: "whole arrays" or "item by item", and on 1.7.2 lists the item
order and degrees (the resize steps depend on the placed element and are added at commit).

Verified live through the tool code on 1.7.2, every node and arc read back exactly (largest
difference 3e-8 degrees):

| Case | Nodes | Result |
| --- | --- | --- |
| New Swept Beam from points, cuts 20 / -10 | 14 | 0.70 s, cuts as sent |
| Update, shrink, no cuts given | 3 | cuts kept through the reset |
| Update to two nodes | 2 | `A = aDone` = plan length |
| Update, grow | 56 | 2.59 s |
| Swept Beam and Road Marking from a Polyline with arcs of 90 and -60 degrees | 4 | arcs read back 90 and -60 |
| New Road Marking, then same count, shrink, grow with a preset change | 4, 4, 2, 14 | settings kept, 1.30 s for 14 |
| Points with a vertical piece | | refused in the dry run |

On MCP-Test (Archicad 29, Tapir 1.7.1) a dry run of both tools still reports whole arrays in the
old order. Test elements were deleted; MCP-Test_27 is back to its 16 elements and was saved.

## What the old code would have done on 1.7.2

- Any new beam or marking with more than two nodes: `CreateObjects` succeeds, the parameter write
  is refused, and a default part is left in the model ("the element exists").
- Two-node paths go through (the merge needs more than two nodes), but an arc sent in radians
  lands in degrees: a 90 degree arc becomes 1.57 degrees. Same-count updates also run the merge
  on every item, in an order that can bring a new x next to an old y (not tried live).
- The Road Marking's same-count trick (`nodeX` as 0, 1, 2 in a call of its own) relied on whole
  array writes not running the merge.

## Follow-ups

- The Road Marking parent spec in the Archicad GDL repo
  (`docs/superpowers/specs/2026-10-07-road-marking-design.md`, "Through the API") describes the 1.7.1
  writes only.
- A size parameter in both parts (resize the arrays when the API writes it) would replace the
  reset and the `extEnd` steps, but placed parts and library copies without it would still need
  this path.
