# Archicad 29 MCP Server — Design

**Date:** 2026-07-16 (revised same day: full API surface added)
**Status:** Approved (pending user review of this document)
**Repo:** https://github.com/alesdev88/Archicad-MCP.git

## Purpose

A cross-platform (macOS + Windows) MCP server that connects AI clients (Claude
Desktop, Claude Code, any MCP client) to a running Archicad 29 instance. It
serves two audiences with one server:

1. **Delivery-readiness QA** — a rules engine that runs BIM QA checks locally
   and returns verdicts (the durable, office-standards product).
2. **Full API access** — the complete official JSON API + Tapir command
   surface, including element creation and modification, exposed through a
   small, well-designed tool set (the office requirement: "basically all API
   calls").

Design informed by the Second Brain research
(`20_projects/_incubator/archicad-mcp-server.md`): Autodesk's Revit MCP shows
few sharp composable tools beat many autogenerated ones (tapir-archicad-MCP's
137 tools need a semantic index because they don't fit in context), and the
rules layer is the only part no vendor will ever ship.

## Decisions (settled)

| Decision | Choice | Why |
|---|---|---|
| Server shape | Three tiers: verdict tools + curated core tools + API gateway | Full API reach without the 137-tool context blowup; rules remain the durable core |
| Language | Python 3.12+ | Multiplatform hard requirement; typed Archicad client exists; ArchicadOprema proves the pattern |
| MCP framework | FastMCP, stdio transport | Standard choice for local desktop MCP servers |
| Archicad transport | `multiconn_archicad` | Wraps official JSON API + Tapir behind one Pydantic-typed interface; multi-instance aware |
| Tapir add-on | Required for writes/creation; reads and verdict rules degrade gracefully without it | The official API cannot create elements at all; core QA reads work official-only |
| Rules definition | Hybrid: YAML rule types + `custom_rules.py` plugin hook | YAML covers the common 90%; Python escape hatch for the rest |
| Rules location | Framework public, rules local | Office standards are amber-tier; real rules live outside the repo (`--rules-dir` / `ARCHICAD_MCP_RULES_DIR`) |
| Privacy | Launch mode: `verdicts` (tier 1 only) vs `full` (everything) | Raw model data to a cloud LLM violates the amber tier on client models; the mode makes the policy explicit and enforceable per launch |
| Rules engine isolation | Zero MCP/transport imports | Survives transport swap when Graphisoft ships official MCP, and v30 API churn |
| Tapir definitions | Bundled snapshot + sync script | Luka Gradišar's server shows the failure mode: a year-stale bundled snapshot missing entire command groups |

## Architecture

```text
MCP layer          FastMCP over stdio — ~22 tools in three tiers,
                   registration filtered by --mode
    ↓
Rules engine       pure library: rule types, YAML loader, plugin hook, verdicts
(tier 1 brain)     — zero imports from MCP or transport code
    ↓
Core ops + gateway curated query/write/create operations; command registry
(tiers 2–3)        for the full official + Tapir surface
    ↓
Transport          multiconn_archicad → running Archicad (official API + Tapir)
                   extractors build ModelSnapshot; actions do write-back
```

The rules seam is `ModelSnapshot`: a typed structure (elements, properties,
classifications, layers, zones, stories) that rules consume. Rules never touch
the API; only `extract.py`/`connection.py` change on API churn (v30) or
transport replacement (official Graphisoft MCP).

## Tool surface (three tiers, ~22 tools)

### Tier 1 — Verdict tools (8) — available in both modes

| Tool | Does | Needs Tapir |
|---|---|---|
| `list_instances` | Running Archicad instances, open project, version, Tapir availability. Required first call | no |
| `get_model_summary` | Element counts by type / story / layer — aggregates only | no |
| `list_rules` | Loaded rules with descriptions, sources, load errors | no |
| `run_rule(rule_id)` | One rule → verdict + failing GUIDs | no |
| `audit_delivery_readiness(ruleset?)` | All rules (or those tagged with the ruleset tag) → scored verdict | no (IFC rules skipped without Tapir) |
| `verify_ifc_export_readiness` | Will required properties/types actually export to IFC | yes |
| `highlight_failures(rule_id)` | Highlight failing elements in Archicad | yes |
| `create_issues_from_failures(rule_id)` | Create Archicad issues from failures | yes |

### Tier 2 — Curated core tools (11) — `full` mode only

Hand-designed, composable, covering the common 90% of API use
(the Autodesk `query_model` lesson):

| Tool | Does | Needs Tapir |
|---|---|---|
| `query_elements(filters)` | One query language: type / story / layer / classification / zone / current selection → GUIDs + counts | no |
| `get_element_data(guids, ...)` | Properties, classifications, details, bounding boxes for given elements | no |
| `set_element_data(...)` | Property/classification/detail writes; `dry_run=true` default — logs intended changes without committing | no |
| `create_elements(type, specs)` | Unified creation: columns, slabs, zones, walls, objects, doors, windows, stairs, texts, meshes... | yes |
| `move_elements(guids, vector)` | Move; `dry_run` default, explicit `confirm` to execute | yes |
| `delete_elements(guids, confirm)` | Delete; refuses without explicit `confirm=true` | yes |
| `manage_selection(get/set/clear)` | Read or change the user's Archicad selection | get: no; set/clear: yes |
| `get_project_info()` | Project info fields, stories, hotlinks, geolocation | partially |
| `list_attributes(type)` | Layers, building materials, composites, surfaces, profiles, zone categories | no |
| `manage_issues(action, ...)` | Create / list / comment / attach elements / BCF export-import | yes |
| `publish(publisher_set)` | Fire a publisher set | yes |

### Tier 3 — API gateway (3) — `full` mode only

| Tool | Does |
|---|---|
| `list_api_commands(group?)` | Catalog of every official JSON API + Tapir command with one-line summaries |
| `describe_api_command(name)` | Full input/output schema for one command |
| `execute_api_command(name, params)` | Execute any command in the catalog |

The gateway is what makes "basically all API calls" true without one tool per
command. The command registry is built from the official API docs surface and
Tapir's `command_definitions.js` / `common_schema_definitions.js`, bundled in
the repo with `scripts/sync_tapir_defs.py` to refresh them from the Tapir repo
(avoiding the stale-snapshot failure mode).

Multi-instance: if exactly one Archicad instance is running it is
auto-selected; if several, tools return the list and require a `port`
parameter.

## Privacy: launch modes

`--mode verdicts|full` (or `ARCHICAD_MCP_MODE`):

- **`verdicts`** — only tier 1 registered. Results contain rule ids, booleans,
  counts, GUIDs, severities, rule messages — never element names, property
  values, or project info (enforced structurally: the `Verdict`/`RuleResult`
  types have no fields for raw data). Safe for client models with a cloud LLM
  under the office amber-tier rule.
- **`full`** — all tiers. Raw model data flows to the LLM by design. For
  non-sensitive test models, or workflows where the office explicitly accepts
  the exposure. `full` is the default when `--mode` is not given.

The README states this trade-off plainly — unlike existing servers whose
"no data leaves your computer" claims cover only tool discovery.

Evaluation and testing run on **non-sensitive test models only** — never a
client project.

## Components

```text
Archicad-MCP/                      (public repo)
├── pyproject.toml                 fastmcp, multiconn_archicad, pydantic, pyyaml
├── src/archicad_mcp/
│   ├── server.py                  FastMCP app, tool registration + mode filter
│   ├── connection.py              instance discovery, Tapir detection
│   ├── extract.py                 API → ModelSnapshot
│   ├── actions.py                 tier-1 write-back: highlight, issues-from-failures
│   ├── core/                      tier-2 curated tools
│   │   ├── query.py               query_elements filter language
│   │   ├── element_data.py        get/set element data, dry-run engine
│   │   ├── create.py              unified create_elements
│   │   ├── mutate.py              move/delete with confirm
│   │   ├── selection.py, project.py, attributes.py, issues.py, publish.py
│   ├── gateway/                   tier-3
│   │   ├── registry.py            command catalog (official + Tapir defs)
│   │   └── execute.py             validated pass-through execution
│   └── rules/                     the engine — importable, transport-free
│       ├── types.py               ModelSnapshot, RuleResult, Verdict
│       ├── engine.py              run rules, aggregate scoring
│       ├── loader.py              YAML + Python plugin discovery
│       └── builtin/               property_required, classification_required,
│                                  layer_compliance, zone_checks, ifc_readiness
├── scripts/sync_tapir_defs.py     refresh bundled Tapir definitions
├── examples/rules/                generic, public-safe example rules
├── docs/superpowers/specs/        this document
└── tests/                         fixtures/ = JSON ModelSnapshots + API replays
```

Only the rule types the first real office checklist needs get built; more rule
types are added when a real rule demands them (YAGNI).

### Local rules directory (outside the repo)

Passed via `--rules-dir` / `ARCHICAD_MCP_RULES_DIR`. Contains `*.yaml` rule
instances and an optional `custom_rules.py` plugin:

```yaml
- id: walls-fire-rating
  type: property-required
  applies_to: { element_type: Wall }
  property: "Fire Rating"
  severity: error
  tags: [ifc-delivery]
```

Rules may carry `tags`; `audit_delivery_readiness(ruleset)` filters by tag, so
rulesets are just tags — no separate ruleset file format. Without a rules dir,
bundled generic example rules load so the server works out of the box. Office
rule files reach colleagues via the internal file share, never the public repo.

## Data flow

**Audit path (tier 1):** client calls `audit_delivery_readiness` → connection
ensured → rule types declare needed data → extractors pull only that →
`ModelSnapshot` → engine runs rules → scored verdict. `score` = percentage of
non-skipped rules passing; overall `pass` is true only when no `error`-severity
rule fails (warnings lower the score but don't fail the audit).

```json
{ "score": 78, "pass": false,
  "results": [{ "rule": "walls-fire-rating", "pass": false,
                "failures": 14, "guids": ["..."], "severity": "error" }] }
```

**Write path (tier 2):** all mutating tools default to `dry_run=true`,
returning the exact intended changes (element + field + old → new value).
Committing requires `dry_run=false` (and `confirm=true` for move/delete). This
mirrors the office's proven script workflow: dry-run, review, write.

**Gateway path (tier 3):** `list_api_commands` → `describe_api_command` →
`execute_api_command`; params are validated against the bundled schema before
hitting Archicad, so schema mismatches produce readable errors, not API
failures.

## Error handling

- Archicad not running / no model open → actionable tool message, never a
  stack trace.
- Multiple instances, no `port` → list instances, ask for the parameter.
- Tapir missing → Tapir-dependent tools say "requires the Tapir add-on" with
  an install pointer; audits mark IFC rules **skipped** (not failed).
- Destructive ops (delete, move, uncommitted writes) → refuse without explicit
  confirm/dry_run=false; never destructive by default.
- Invalid YAML rule → collected at startup, reported via `list_rules`; valid
  rules still load.
- Unknown/mismatched gateway command → schema validation error naming the
  command and expected shape; suggest `sync_tapir_defs` if versions mismatch.
- v30 API churn quarantined in `extract.py` / `connection.py` / bundled
  definitions; `list_instances` reports the Archicad version.

## Testing

- **Rules engine:** pytest against JSON fixture `ModelSnapshot`s — offline,
  the bulk of the suite. TDD.
- **Core tools:** mocked `multiconn_archicad` transport; dry-run output
  asserted exactly; destructive-op guards tested.
- **Gateway:** registry parsing of real definition files; schema validation
  cases; execution against mocked transport.
- **Loader:** YAML parsing/validation incl. malformed rules.
- **MCP layer:** FastMCP in-memory client tests over all tools in both modes
  (mode filter verified).
- **Live integration:** pytest marker `live`, run manually against a
  non-sensitive test model on macOS and Windows.
- **CI:** GitHub Actions on macOS + Windows + Linux runners.

## Distribution (minimal, v1)

README documents: `uv tool install git+https://github.com/alesdev88/Archicad-MCP.git`
(or `uvx`) for macOS and Windows; Claude Desktop and Claude Code config
snippets for both OSes including `--mode` and `ARCHICAD_MCP_RULES_DIR`; Tapir
add-on install pointer; the privacy-mode explanation.

## Out of scope (v1)

- Snapshot persistence, trend tracking, HTML reports (delivery-intelligence
  ideas live in their own project).
- A semantic search index over commands (the gateway's list/describe flow
  covers discovery; revisit only if it proves clumsy).
- Any distribution beyond the README (no PyPI, no installers).

## Watch list (from research, unchanged)

- Graphisoft official MCP ("coming soon") — may overtake tiers 2–3; the rules
  engine and tool shapes survive.
- Archicad v30 — API churn lands in `extract.py`/`connection.py`/definitions.
- Tapir releases — run `sync_tapir_defs.py` on add-on updates.
