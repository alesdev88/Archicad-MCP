# Archicad 29 MCP Server — Design

**Date:** 2026-07-16
**Status:** Approved (pending user review of this document)
**Repo:** https://github.com/alesdev88/Archicad-MCP.git

## Purpose

A cross-platform (macOS + Windows) MCP server that connects AI clients (Claude
Desktop, Claude Code, any MCP client) to a running Archicad 29 instance and
answers delivery-readiness questions about the live model. It is a
**rules/verdicts server**, not a generic API wrapper: a small set of sharp,
hand-designed tools that run BIM QA rules locally and return judgments — never
raw model data.

This implements Phase 1 of the Second Brain research
(`20_projects/_incubator/archicad-mcp-server.md`), which compared the Autodesk
Revit Public MCP (7 hand-designed read-only tools) with tapir-archicad-MCP
(137 autogenerated tools) and concluded: few sharp tools win, and the only
defensible product is one that encodes our own delivery standards.

## Decisions (settled)

| Decision | Choice | Why |
|---|---|---|
| Server shape | Rules/verdicts server | Generic servers get overtaken by Graphisoft's official MCP ("coming soon" on their roadmap); encoded standards do not |
| Language | Python 3.12+ | Multiplatform hard requirement; only ecosystem with a typed Archicad client; ArchicadOprema proves the pattern works |
| MCP framework | FastMCP, stdio transport | Standard choice for local desktop MCP servers |
| Archicad transport | `multiconn_archicad` | Wraps official JSON API + Tapir behind one Pydantic-typed interface; multi-instance aware |
| Tapir add-on | Optional, graceful degradation | Official API covers all core read rules; Tapir adds highlight, issues, IFC/GDL. Easiest install for colleagues |
| Rules definition | Hybrid: YAML rule types + Python plugin hook | YAML covers the common 90%; `custom_rules.py` escape hatch for the rest |
| Rules location | Framework public, rules local | Office standards are amber-tier (privacy); real rules live outside the repo, loaded via `--rules-dir` / `ARCHICAD_MCP_RULES_DIR` |
| Privacy | Verdicts only, never raw data | Amber-tier constraint and better tool design; enforced structurally in the result types |
| Rules engine isolation | Zero MCP/transport imports | Survives transport swap when Graphisoft ships official MCP, and v30 API churn |

## Architecture

Three layers in one Python package, one hard seam:

```text
MCP layer          FastMCP over stdio — 8 tools, formats verdicts for the model
    ↓
Rules engine       pure library: rule types, YAML loader, plugin hook, verdict types
                   — zero imports from MCP or transport code
    ↓
Transport          multiconn_archicad → running Archicad (official API + Tapir)
                   extractors build ModelSnapshot; actions do write-back
```

The seam is `ModelSnapshot`: a typed structure (elements, properties,
classifications, layers, zones, stories) that rules consume. Rules never touch
the API. Extractors produce snapshots; when the API changes (v30) or the
transport is replaced (official Graphisoft MCP), only `extract.py` and
`connection.py` change.

Write-back (highlight failing elements, create issues) is an **action module**
in the transport layer that takes GUIDs from a verdict. It is not a rule
concern.

## Tool surface (8 tools)

| Tool | Does | Needs Tapir |
|---|---|---|
| `list_instances` | Running Archicad instances, open project, Archicad version, Tapir availability. Required first call | no |
| `get_model_summary` | Element counts by type / story / layer — aggregates only | no |
| `list_rules` | Loaded rules with descriptions, sources, and any load errors | no |
| `run_rule(rule_id)` | One rule → verdict + failing GUIDs | no |
| `audit_delivery_readiness(ruleset?)` | All rules (or those tagged with the given ruleset tag) → scored verdict | no (IFC rules skipped without Tapir) |
| `verify_ifc_export_readiness` | Will required properties/types actually export to IFC | yes |
| `highlight_failures(rule_id)` | Highlight failing elements in the Archicad window | yes |
| `create_issues_from_failures(rule_id)` | Create Archicad issues from failures | yes |

Multi-instance: if exactly one Archicad instance is running it is
auto-selected; if several, tools return the list and require a `port`
parameter.

## Components

```text
Archicad-MCP/                      (public repo)
├── pyproject.toml                 fastmcp, multiconn_archicad, pydantic, pyyaml
├── src/archicad_mcp/
│   ├── server.py                  FastMCP app, the 8 tools
│   ├── connection.py              instance discovery, Tapir detection
│   ├── extract.py                 API → ModelSnapshot
│   ├── actions.py                 highlight_elements, create_issues (Tapir)
│   └── rules/                     the engine — importable, transport-free
│       ├── types.py               ModelSnapshot, RuleResult, Verdict
│       ├── engine.py              run rules, aggregate scoring
│       ├── loader.py              YAML + Python plugin discovery
│       └── builtin/               parameterized rule types:
│                                  property_required, classification_required,
│                                  layer_compliance, zone_checks, ifc_readiness
├── examples/rules/                generic, public-safe example rules
├── docs/superpowers/specs/        this document
└── tests/                         fixtures/ = JSON ModelSnapshots
```

Only the rule types the first real office checklist needs get built; more rule
types are added when a real rule demands them (YAGNI).

### Local rules directory (outside the repo)

Passed via `--rules-dir` flag or `ARCHICAD_MCP_RULES_DIR` env var. Contains
`*.yaml` rule instances and an optional `custom_rules.py` plugin:

```yaml
- id: walls-fire-rating
  type: property-required
  applies_to: { element_type: Wall }
  property: "Fire Rating"
  severity: error
  tags: [ifc-delivery]
```

Rules may carry `tags`; `audit_delivery_readiness(ruleset)` filters by tag, so
rulesets are just tags — no separate ruleset file format.

Without a rules dir, the server loads the bundled generic example rules so it
works out of the box for evaluation.

Office rule files are distributed to colleagues via the internal file share,
never committed to the public repo.

## Data flow

1. MCP client calls `audit_delivery_readiness`.
2. Server ensures a connection (auto-select single instance).
3. Rule types declare what data they need; extractors pull **only that** and
   build a `ModelSnapshot`.
4. Engine runs each rule against the snapshot → `RuleResult`s → scored
   `Verdict`.
5. Scoring: `score` is the percentage of non-skipped rules that pass. The
   audit's overall `pass` is true only when no `error`-severity rule fails;
   failing `warning`-severity rules lower the score but do not fail the audit.
6. Tool returns JSON:

```json
{ "score": 78, "pass": false,
  "results": [{ "rule": "walls-fire-rating", "pass": false,
                "failures": 14, "guids": ["..."], "severity": "error" }] }
```

7. Optionally `highlight_failures(rule_id)` → `actions.py` → Tapir
   `HighlightElements`.

### Privacy (verdicts-only, enforced structurally)

`Verdict` and `RuleResult` have **no fields** for element names, property
values, or project info — only rule ids, booleans, counts, GUIDs, severities,
and rule messages. Value comparisons (code lists, required values) happen
locally; only pass/fail leaves the machine. The feedback loop closes through
`highlight_failures` in Archicad, not through data dumps to the LLM.

`get_model_summary` returns aggregate counts only.

Evaluation and testing run on **non-sensitive test models only** — never a
client project (privacy-tiers rule).

## Error handling

- Archicad not running / no model open → actionable tool message ("Start
  Archicad 29 and open a project"), never a stack trace.
- Multiple instances, no `port` given → list instances, ask for the parameter.
- Tapir missing → Tapir-dependent tools return "requires the Tapir add-on"
  with an install pointer; `audit_delivery_readiness` marks IFC rules
  **skipped** (not failed) with a note.
- Invalid YAML rule → collected at startup, reported via `list_rules` and the
  server log; valid rules still load.
- v30 API churn is quarantined in `extract.py` / `connection.py`;
  `list_instances` reports the Archicad version so mismatches are visible.

## Testing

- **Rules engine:** pytest against JSON fixture `ModelSnapshot`s — fully
  offline, no Archicad needed. This is the bulk of the test suite. TDD.
- **Loader:** YAML parsing and validation, including malformed-rule handling.
- **Extractors/connection:** mocked `multiconn_archicad` responses.
- **MCP layer:** FastMCP in-memory client tests over the tool surface.
- **Live integration:** pytest marker `live`, run manually against a
  non-sensitive test model on macOS and Windows.
- **CI:** GitHub Actions on macOS + Windows + Linux runners — this is what
  makes "cross-platform" a verified property rather than a hope.

## Distribution (minimal, v1)

README documents:

- `uv tool install git+https://github.com/alesdev88/Archicad-MCP.git` (or
  `uvx`), macOS and Windows.
- Claude Desktop and Claude Code MCP config snippets for both OSes, including
  `ARCHICAD_MCP_RULES_DIR`.
- Tapir add-on install pointer (optional).

## Out of scope (v1)

- Element creation / model mutation beyond highlight + issues.
- Snapshot persistence, trend tracking, HTML reports (delivery-intelligence
  ideas live in their own project).
- Publishing/publisher-set automation.
- GDL parameter rules (add a rule type when a real rule needs it).
- Any distribution beyond the README (no PyPI, no installers).

## Watch list (from research, unchanged)

- Graphisoft official MCP ("coming soon") — when it lands, swap the transport;
  the rules engine survives.
- Archicad v30 — API churn lands in `extract.py`/`connection.py` only.
